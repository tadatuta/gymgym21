# Runbook Gym21

Проверено по исходникам 8 сентября 2026 (T06). Все команды ниже выполняются из корня репозитория, если явно не сказано иначе. [Краткая архитектура](architecture.md), [ход аудита](../AUDIT_PROGRESS.md).

`gym21` объединяет клиент и сервер в одном npm-workspaces репозитории.

## Структура

- `packages/contracts` — общие runtime-схемы и wire-типы
- `apps/client` — Vite/PWA клиент
- `apps/server` — Express + Better Auth backend
- `infra/nginx` — reverse proxy для single-origin docker-развёртывания
- `secrets` — локальная директория для внешних секретов, включая optional Google credentials

## Локальная разработка

Требования:

- Node.js 22.23.2 LTS (`nvm install && nvm use`, версия закреплена в `.nvmrc`)
- npm 10+
- Docker Desktop или совместимый `docker compose`

Установка зависимостей:

```bash
nvm install
nvm use
npm ci
```

Создайте корневой `.env` по `.env.example`, задайте `DATABASE_URL` для локальной
PostgreSQL и `BETTER_AUTH_SECRET`. База должна быть запущена до старта сервера.
Dev-команда автоматически читает только `<корень проекта>/.env`; файл
`apps/server/.env` не используется. Уже экспортированные переменные окружения
имеют приоритет над файлом. Если все настройки экспортированы, `.env` не нужен.

Из корня можно запустить оба процесса командой `npm run dev` или по отдельности:

```bash
npm run dev:server
npm run dev:client
```

Та же серверная команда доступна из workspace: `cd apps/server && npm run dev`
(или из корня `npm run dev --workspace @gym21/server`). Во всех трёх случаях
путь к `.env` один и тот же. После изменения `.env` перезапустите команду.
Сервер использует `tsx watch`: запускается с чистым/отсутствующим `dist` и
перезапускается при изменениях импортированных исходников. Ошибки преобразования
TypeScript и запуска остаются в терминале; watcher ждёт исправления. `Ctrl+C`
останавливает watcher и сервер. Проверка типов выполняется отдельно через
`npm run typecheck`; production по-прежнему использует `tsc` и `node dist/server.js`.

Общие runtime-схемы и выводимые из них wire-типы находятся в `packages/contracts`
(`@gym21/contracts`). Клиентские записи уточняют локальные поля отдельно; SQL row-типы
остаются на сервере. Vite читает исходники пакета через `browser` export, а `tsx watch`
использует условие `gym21-source`, поэтому правки общих схем видны без пересборки.
Production Node загружает `dist/*.js`; `npm run build` сервера сначала собирает
контракты, в том числе при запуске из `apps/server`. Отдельная проверка контрактов:
`npm run test --workspace @gym21/contracts`. Изолированная проверка чистой установки
и package exports: `node audit/contracts-packaging.mjs` (использует npm offline cache; `--online` разрешает загрузку недостающих пакетов).

Production `start` ожидает окружение от оболочки/контейнера и сам `.env` не читает.

В dev-режиме клиент использует Vite proxy и ходит в backend через относительные `/api`-пути.

## Проверки

```bash
npm run check
```

Команда последовательно выполняет `typecheck`, `lint`, `test` и `build` для контрактов, клиента и сервера. Ошибка любого пакета останавливает следующие пакеты и этапы с ненулевым exit code. Каждый этап доступен отдельно: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`; отдельный пакет — через `--workspace @gym21/client` (также `contracts` и `server`). ESLint проверяет TypeScript-исходники всех пакетов; сервер использует Node globals, клиент сохраняет свою конфигурацию. TypeScript запрещает unused locals/parameters во всех трёх пакетах. Audit-скрипты и серверные JS fixtures в это lint-покрытие не входят.

Обычный `npm test` явно отмечает PostgreSQL-тесты как skipped без `GYM21_TEST_DATABASE_URL`; такой результат не подтверждает интеграцию с БД. Обязательный прогон всей серверной suite с PostgreSQL:

```bash
GYM21_TEST_DATABASE_URL=<disposable-postgres-url> npm run test:integration
```

Команда до сборки и импорта тестов отклоняет отсутствующий или некорректный PostgreSQL URL без вывода его содержимого и никогда не использует `DATABASE_URL` как запасное значение. Используйте только отдельную тестовую БД: тесты создают собственные UUID-схемы и удаляют их после прогона. Полный `check` также запускает PostgreSQL-тесты, если передать ему эту переменную. TLS fixture требует отдельного `GYM21_TLS_TEST_URL`, поэтому один TLS-тест может оставаться skipped даже при обычном PostgreSQL-прогоне; отдельная воспроизводимая проверка — `node audit/postgres-tls.mjs`, условия в [TLS runbook](../audit/postgres-tls.md).

[GitHub Actions CI](../.github/workflows/ci.yml) запускается на каждый push и pull request: Ubuntu 24.04, Node из `.nvmrc` (22.23.2), npm cache по корневому `package-lock.json`, затем `npm ci`, `npm run check` и `npm run test:integration`. Интеграционный этап получает только URL отдельного PostgreSQL 16 service с синтетическими реквизитами; readiness проверяет `pg_isready`. Обычный `check` выполняется без URL БД, поэтому PostgreSQL-покрытие подтверждает следующий обязательный этап. Затем CI устанавливает Chromium с системными зависимостями и выполняет `npm run test:browser` с тем же отдельным PostgreSQL service. TLS и большие performance fixtures остаются адресными. Тесты сами задают синтетическое auth-окружение; секреты репозитория и `.env` не требуются. Job ограничен 20 минутами, предыдущий запуск того же события/ref отменяется новым; токен имеет только `contents: read`, checkout не сохраняет credentials. Service удаляется GitHub после job, даже при ошибке или отмене.

Workflow добавлен в T02; первый запуск на GitHub проверяется после push (локальные проверки не подтверждают работу hosted runner). Покрытие настоящего repository и миграций сверено в T03: [матрица PostgreSQL](../audit/postgres-tests.md). T04 добавляет [настоящие auth endpoints и Chromium logout503](../audit/auth-endpoints.md); его browser fixture включён в T05 suite. T05 добавляет `npm run test:browser:install` и `GYM21_TEST_DATABASE_URL=<disposable-postgres-url> npm run test:browser`: [сценарии, ограничения и реальные SW lifecycle проверки](../audit/browser-tests.md). T06 завершён: [общие wire fixtures и итоговые доказательства](../audit/completion.md). `node audit/reproduce.mjs` и `node audit/reproduce-server.mjs` — совместимые entrypoints для check и обязательной PostgreSQL integration suite соответственно; это текущие регрессии с ожидаемым правильным поведением. Дополнительные audit-сценарии описаны в [каталоге проверок](../audit/README.md). Конфигурация сверена с [официальным setup-node](https://github.com/actions/setup-node), [checkout](https://github.com/actions/checkout) и [документацией PostgreSQL services](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

## Client HTML Safety

- Пользовательские строки нельзя вставлять в HTML-шаблоны напрямую: для текста используйте `escapeHtml`, для атрибутов `escapeAttribute`, для ссылок и изображений сначала `sanitizeUrl`.

## Offline-first

- После первого подтверждённого входа клиент сохраняет только несекретный descriptor аккаунта и открывает локальную IndexedDB до сетевой проверки сессии.
- Каждому `storageKey` соответствует отдельная IndexedDB; данные разных аккаунтов не смешиваются.
- Доменные изменения и запись в deduplicated outbox выполняются одной IndexedDB-транзакцией.
- Sync использует поколения outbox-записей, явные server acknowledgements, entity versions и постраничный pull. Изменение, сделанное во время запроса, не удаляется его устаревшим ответом.
- Конфликтующий локальный payload сохраняется и доступен для восстановления в разделе «Профиль → Данные».
- HttpOnly Better Auth cookie остаётся единственным источником сетевой авторизации. Токены и cookie не копируются в offline descriptor.
- Первый вход, синхронизация, Passkey/Telegram-операции и генерация новых AI-рекомендаций требуют сеть. Последние AI-результаты и ранее открытые публичные профили кэшируются внутри базы текущего аккаунта.

## Docker Deploy

1. Создать `.env` на основе `.env.example`. Заполнить `POSTGRES_PASSWORD` и `BETTER_AUTH_SECRET` разными случайными секретами (не менее 32 символов; например, каждый отдельно через `openssl rand -hex 32`). Пустые значения блокируют Compose, короткие/старые значения блокируют запуск API. Для существующего volume изменение `.env` не меняет пароль роли PostgreSQL: сначала согласованно обновите пароль существующей роли, затем конфигурацию; volume не удаляйте.
2. При необходимости AI положить Google credentials в `./secrets/google-application-credentials.json`.
3. Поднять стек:

```bash
npm run docker:up
```

Сервисы:

- `proxy` — единая точка входа на `http://localhost:${APP_PORT}`
- `client` — статический SPA container
- `server` — Express API и auth
- `postgres` — единственное runtime-хранилище данных

Compose фиксирует API на `0.0.0.0:8788`, как в upstream Nginx. `PORT` и `HOST` из `.env` применяются только при нативном запуске; внешний порт меняется через `APP_PORT`. Compose строит `DATABASE_URL` из тех же `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`, что использует PostgreSQL, с URL-encoding; отдельный `DATABASE_URL` применяется только при нативном запуске (там укажите `localhost` и порт БД).

PostgreSQL в базовом стеке доступен только внутри Docker. Ранее локальная правка публиковала `5432:5432`; для сохранения доступа локальных инструментов теперь явно подключайте dev override:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build
```

Он публикует только `127.0.0.1:${POSTGRES_HOST_PORT:-5432}`; при занятом порте задайте `POSTGRES_HOST_PORT=5433`. Для production используйте базовый файл без override. Все `RATE_LIMIT_*`, `AI_*` и настройки Telegram из примера передаются API явно.

Серверный образ устанавливает только production-зависимости server/contracts и содержит compiled `dist`, SQL-миграции и Docker startup wrapper. Он запускается пользователем `node`; nginx клиента остаётся на внутреннем порту 80. Корневая `.dockerignore` исключает env/секреты, локальные данные и build/test outputs. JSON допускается только для явно перечисленных package manifests/lockfile/tsconfig: при добавлении необходимых JSON-ресурсов обновите allowlist.

Проверка реальных образов: `node audit/docker-runtime.mjs`. Нужен Docker; скрипт копирует только tracked исходники в временный контекст, добавляет синтетические canary-файлы и проверяет их исключение, production dependencies/nonroot, миграции и HTTP auth/health с отдельной PostgreSQL, SPA/assets/service worker клиента. Созданные контейнеры, сеть, образы и временный контекст удаляются; рабочие `.env` и пользовательские данные не читаются.

Проверка конфигурации без запуска контейнеров и чтения рабочей `.env`: `node audit/compose-config.mjs` (нужен Docker Compose; используются временные синтетические env-файлы).

Persistent data:

- `postgres_data` — данные Postgres

## Legacy Import

- Runtime работает только с PostgreSQL; file-backed storage и snapshot endpoints удалены.
- Для переноса старых JSON используйте отдельный importer:

```bash
npm run build --workspace @gym21/server
npm run import:storage-json --workspace @gym21/server -- --dir /absolute/path/to/legacy-storage --dry-run --report /absolute/path/to/import-report.json
npm run import:storage-json --workspace @gym21/server -- --dir /absolute/path/to/legacy-storage --manifest /absolute/path/to/import-manifest.json --apply --report /absolute/path/to/import-report.json
```

Замените `/absolute/path/to/…` реальными абсолютными путями. npm workspace запускает importer из `apps/server`, поэтому относительные пути отсчитываются от этой директории, а не корня репозитория.

- Importer поддерживает `--dry-run`, `--apply`, `--manifest`, `--skip-invalid`, `--truncate-storage`, `--report` и `--verbose`.
- `manifest` — массив `{ "sourceKey": "имя-файла-без-json", "storageKey": "целевой-ключ", "userId": "существующий-user-id" }`; `storageKey` и `userId` необязательны. Дубли источников, целевых ключей и пользователей, отсутствующие файлы, чужие привязки и конфликты публичных имён прерывают весь импорт. Уже привязанного пользователя нельзя перенести на другой ключ этим инструментом.
- Сначала проверяются **все** JSON-файлы и manifest. `--dry-run` проверяет только файлы, не подключается к БД и не запускает миграции; проверки существующих привязок, публичных имён и полноты покрытия выполняются при `--apply`. Legacy-файлы могут опускать массивы, `profile.id/isPublic/createdAt` и `workouts[].isManual/pauseIntervals`; неверные явно переданные значения отвергаются.
- `--apply` записывает весь план и привязки одной транзакцией. При ошибке записи откатывается весь план; `processed` заполняется только после commit. `--skip-invalid` разрешает пропустить только повреждённые/невалидные файлы (они перечислены в `skipped`); ошибки manifest, ownership и БД всегда завершаются ненулевым кодом без частичного импорта.
- `--truncate-storage` требует валидной замены **каждого существующего storage root**, запрещает пропуски даже с `--skip-invalid` и не выполняет SQL TRUNCATE. Замена сохраняет монотонные ревизии, tombstones отсутствующих записей и квитанции старых batch, чтобы активные устройства увидели удаления, а повтор старого запроса не восстановил прежние данные. Непокрытые хранилища не удаляются.
- `--report` должен находиться вне каталога источников и не совпадать с manifest (учитываются symlinks). Итоговый JSON также выводится в stdout. При `--apply` после файловой проверки запускаются обычные миграции; импорт кратковременно блокирует запись в storage roots и таблицы ownership, поэтому большие импорты следует выполнять в сервисное окно.

## Env Notes

- Для Docker `APP_BASE_URL`, `AUTH_BASE_URL` и `ALLOWED_ORIGINS` должны указывать на внешний origin proxy.
- `TRUST_PROXY` должен соответствовать реальной схеме reverse proxy, иначе IP-based rate limiting будет считать клиентов некорректно.
- Guardrails для чувствительных маршрутов настраиваются через `RATE_LIMIT_*`: отдельно для auth, username-check, storage/sync и AI.
- PostgreSQL TLS: `DATABASE_SSL=true` проверяет цепочку сертификата и имя сервера; для частного CA укажите `DATABASE_SSL_CA_FILE` с PEM bundle, доступным процессу при запуске. `false` явно отключает TLS для локальной БД. SSL-параметры в `DATABASE_URL` отклоняются; `PGSSLMODE` не меняет режим. CA передаётся через read-only mount, не включается в образ. Настройка, переход и проверка: [PostgreSQL TLS](../audit/postgres-tls.md).
- Backend требует валидный `DATABASE_URL`. Auth и storage используют один PostgreSQL pool и файлы `apps/server/migrations/*.sql`; новые изменения схемы добавляются отдельным файлом, применённые файлы не редактируются. Runner при старте удерживает session advisory lock для текущих database/schema до завершения проверки и применения миграций, включая создание `app_migrations`. Каждый файл и его запись в журнале выполняются в одной транзакции. При ошибке файл откатывается, блокировка освобождается, следующий вызов готовности может повторить попытку; старт/успех/ошибка выводятся с именем файла без SQL и реквизитов подключения. `006_auth_schema.sql` сохраняет существующие auth-таблицы и добавляет отсутствующий `telegram_username`.
- Закрытие `closeDatabasePool` или совместимого `closeAuthPool` завершает общий pool. После повторного открытия `getAuth` и `createAuthNodeHandler` создают экземпляры для нового pool; уже смонтированный HTTP handler относится к прежнему lifecycle приложения, поэтому приложение при таком перезапуске создаётся заново.
- Для `POST /api/me/ai/recommendations` стоит держать консервативные `RATE_LIMIT_AI_*`, `AI_TIMEOUT_MS` и `AI_MAX_OUTPUT_TOKENS`, чтобы ограничивать burst-нагрузку и стоимость одного вызова.
- `AI_MODEL` выбирает модель; по умолчанию сохранена `gemini-3-flash-preview`. При изменении доступности preview-модели задайте поддерживаемую вашим Vertex AI проектом модель в окружении.
- До запроса AI клиент подтверждает синхронизацию профиля и истории, отсутствие конфликтов и пустой outbox. API требует `expectedRevision` и читает весь контекст в одном PostgreSQL snapshot; при изменении ревизии отвечает `409 AI_CONTEXT_STALE` с предложением синхронизироваться и повторить запрос. Изменения, сделанные уже во время генерации, остаются в очереди следующей синхронизации.
- Таймаут и отключение клиента отменяют HTTP-транспорт Google SDK. Слот `RATE_LIMIT_AI_MAX_CONCURRENT` удерживается до фактического завершения операции SDK, даже если она игнорирует отмену, а клиент уже получил `503 AI_TIMEOUT`. Это локальная отмена: после принятия запроса провайдером остановка удалённых вычислений и списаний не гарантируется. Автоматических повторов генерации нет.
- `AI_MAX_CONTEXT_CHARS`, `AI_MAX_RECENT_LOGS`, `AI_MAX_EXERCISE_COUNT` и `AI_TEXT_FIELD_MAX_LENGTH` ограничивают размер пользовательского контекста перед отправкой в модель.
- Browser-сессия опирается на secure Better Auth cookies; клиент не хранит bearer token в `localStorage` и не использует его как источник истины для auth.
- AI endpoint работает только при наличии корректного Vertex AI конфига и credentials; без них backend отвечает явной конфигурационной ошибкой.
- При превышении rate limit сервер возвращает `429 RATE_LIMIT_EXCEEDED`, а при конкурирующих дорогих запросах вроде AI/sync может вернуть `503 ROUTE_BUSY`.
- Sync-запросы и ответы требуют `protocolVersion: 1`; каждый ответ sync/backup требует явный массив `acknowledged` (пустой массив ничего не подтверждает). Запрос без версии получает `400 INVALID_REQUEST` с полем `protocolVersion`, неподдерживаемая версия — `409 UNSUPPORTED_PROTOCOL`, до записи данных. Клиент отклоняет ответы без версии/подтверждений или с другой версией до изменения IndexedDB, cursor, конфликтов и outbox. Миграции реальных старых данных IndexedDB/localStorage и legacy backup сохраняются независимо от wire-протокола.
- После обновления sync wire contract клиент и backend должны деплоиться вместе. Если браузер удерживает старый PWA shell, может понадобиться одноразовый refresh.

### Размеры синхронизации и резервных копий

Обычный sync отправляет не более 500 сущностей и 512 КиБ сериализованного JSON
(UTF-8) за запрос; оставшаяся outbox автоматически планирует следующие пачки.
Одна слишком большая запись остаётся локально: сократите её содержимое и повторите
синхронизацию. Остальные подходящие записи отправляются до показа этой ошибки.
Pull возвращает страницу 1000 сущностей по умолчанию (`limit`: 1–2000), включая
запросы с push. Ответ дополнительно содержит актуальные версии отправленных
сущностей (всего не более `limit + 500`), а cursor отражает только страницу pull.
Старые клиенты с большими push получат 413: обновите клиент; страницы нужно читать
до `hasMore=false`.

Атомарный backup merge/replace не разбивается на sync-пачки: допускается до 100000
logs, но весь JSON должен уложиться в HTTP-лимит. Полный ответ нужен для локального
применения результата. По умолчанию API `JSON_BODY_LIMIT=10mb` и nginx
`client_max_body_size 10m` согласованы (10 МиБ). При изменении лимита меняйте обе
настройки; меньший лимит любого внешнего прокси также действует. Превышение даёт
413, данные не обрезаются и транзакция импорта не начинается. Перед повышением
лимитов учитывайте память и длительность транзакции. Это не меняет отдельные
ограничения CLI-импортёра.

Лимит частоты sync действует на каждую пачку: большая очередь может получить 429. Клиент автоматически повторяет временные сетевые ошибки, 429 и 5xx с задержкой и учётом `Retry-After`; outbox сохраняется. После события `online` повторно проверяется аккаунт и запускается sync без перезагрузки. Для ручной попытки есть «Повторить подключение». Ошибки авторизации, конфликты и невалидные записи требуют соответствующего действия пользователя.

Большая браузерная регрессия: `node audit/sync-batching-browser.mjs` на Node 22
после установки workspace-зависимостей и Playwright с Chromium. Если Playwright
установлен отдельно, задайте `PLAYWRIGHT_MODULE_PATH` (путь к `playwright/index.mjs`);
для отдельного исполняемого файла Chromium — `PLAYWRIGHT_CHROMIUM_EXECUTABLE`.
Сценарий запускает временный Vite и новый браузерный профиль, не читает `.env`,
создаёт 10001 синтетическую запись и проверяет автоматические 21 пачку с настоящим
IndexedDB. API подменён; проверка rate limiter и PostgreSQL выполняется отдельно.

### Дни и длительность тренировок

`profile.timeZone` хранит IANA-зону владельца. История, календарь, статистика,
группировка новых неявных тренировок и формы даты используют её; публичный
профиль передаёт ту же зону посетителю. Для старого профиля клиент временно
использует зону браузера и сохраняет её один раз после полного успешного pull,
проверяя актуальный аккаунт и повторно читая профиль в транзакции. До первого
такого визита сервер использует UTC. Уже сохранённая зона не меняется при
путешествии или входе с другого устройства; изменить её можно в профиле.
Миграция `004_training_time_zone.sql` добавляет поле и очищает публичный кэш.
Существующие timestamps остаются теми же моментами времени.

Формы показывают время в зоне профиля. Новое время, которое отсутствует либо
повторяется при переводе часов, отклоняется с сообщением; неизменённое время
сохраняет исходный instant, секунды и миллисекунды. Перенос подхода обновляет
границы исходной и целевой неявной сессии вместе с outbox в одной транзакции;
пустая исходная сессия получает tombstone, ручная сессия сохраняет свои границы.

Карточка, график и средняя длительность используют одну модель в секундах:
максимум из времени сессии без пауз и суммы введённых длительностей подходов.
Перекрывающиеся паузы вычитаются один раз и ограничиваются границами сессии.
Браузерная регрессия: `node audit/training-time-browser.mjs` с теми же
`PLAYWRIGHT_MODULE_PATH` и `PLAYWRIGHT_CHROMIUM_EXECUTABLE`, что указаны выше.
Она проверяет настоящий IndexedDB и обработчик формы в изолированном Chromium,
при разных зонах владельца и браузера, без `.env` и пользовательских данных.

Проверка dev lifecycle: `GYM21_TEST_DATABASE_URL=<disposable-postgres-url> node audit/dev-runtime.mjs`
на Node 22.23.2. Создаёт временную копию исходников и отдельную PostgreSQL-схему,
проверяет root/workspace startup, env precedence, restart/error recovery и Ctrl+C
без оставшихся дочерних процессов; удаляет временную копию и схему.


### Публичная история и ограниченные SQL-чтения

`GET /api/profiles/:identifier` возвращает общую статистику за всю историю и последние 14 активных дней в часовом поясе владельца. При включённой полной истории ответ содержит не более 100 подходов, только используемые этой страницей упражнения, `activityDays` для шестимесячной тепловой карты и `history.nextCursor` (`null` в конце). Следующая страница запрашивается тем же endpoint с `?cursor=…`; интерфейс предлагает «Загрузить ещё». Курсор привязан к хранилищу и ревизии; `409 PUBLIC_HISTORY_STALE` требует обновить профиль с первой страницы. Некорректный курсор — `400 INVALID_HISTORY_CURSOR`; скрытый профиль — `404`. Каждая страница заново проверяет доступность профиля. Метаданные sync и личные поля профиля в истории не передаются.

Публичный endpoint ограничен по IP: `RATE_LIMIT_PUBLIC_WINDOW_MS=60000`, `RATE_LIMIT_PUBLIC_MAX=60`, `RATE_LIMIT_PUBLIC_MAX_CONCURRENT=4`; превышение возвращает `429` и `Retry-After`. Счётчики и слоты одновременных операций общие для всех процессов, подключённых к одной PostgreSQL/schema; при недоступности store admission возвращает `503 RATE_LIMIT_UNAVAILABLE`. AI читает не более `AI_MAX_EXERCISE_COUNT` типов и `AI_MAX_RECENT_LOGS` подходов непосредственно через SQL LIMIT; неиспользуемые сессии тренировок не читает. Исторические агрегаты по-прежнему сканируют историю в PostgreSQL на промахе кэша, но не загружают её целиком в Node.js. Воспроизводимые планы и ограничения: [audit/public-query-performance.md](../audit/public-query-performance.md).


Операционная готовность API: `/health` — liveness процесса, `/ready` — завершённые миграции, доступная БД (короткий `SELECT 1`) и отсутствие shutdown/неопределённого владения слотом. Readiness отвечает `503` при сбое; Compose проверяет `/ready`, proxy ждёт healthy server. Это стартовая зависимость: Compose сам по себе не перезапускает контейнер, ставший unhealthy.

Все ожидания ограничены конфигурацией: подключение БД 5с, SQL 120с, клиентское ожидание SQL 125с; для миграций отдельные 600с на SQL, общий startup 610с. HTTP headers/body 15/30с, idle 130с, keepalive 5с; shutdown 15с. Большой backup/import по-прежнему атомарен, но может потребовать увеличения SQL/HTTP бюджета на медленной БД. При shutdown сначала прекращается admission новых соединений, затем закрываются HTTP и общий auth/storage pool; по дедлайну sockets/активные DB connections закрываются принудительно. Compose grace 20с нужно увеличить вместе с `SHUTDOWN_TIMEOUT_MS`.

Общий auth IP-limit покрывает все изменяющие запросы (включая встроенные password signup/signin и recovery), Telegram/migration, а также GET challenge passkey; username check имеет отдельный budget. Дополнительная встроенная защита Better Auth остаётся. Для public/sync/AI общая аренда слота живёт 60с и продлевается каждые 15с до завершения фактического promise, в том числе после timeout/disconnect/игнорируемого AI abort. Потеря подтверждения аренды закрывает ответ, делает процесс unready и блокирует новые admission до восстановления аренды или завершения операции. После crash аренда истекает; сетевой раздел/долгая остановка процесса могут допустить перекрытие внешнего вычисления с новой арендой на другом процессе. Abort SDK не гарантирует остановку вычислений или биллинга провайдера. Настройки, тесты и runbook: [audit/runtime-limits.md](../audit/runtime-limits.md).


## Резервная копия аккаунта

В «Профиль → Данные» экспортируйте JSON перед восстановлением. Формат backup v1 поддерживает merge и replace. Онлайн импорт выполняется атомарно с проверкой `expectedRevision`; при конкурентном изменении сначала синхронизируйтесь. Офлайн доступен только merge: изменения и outbox записываются одной локальной транзакцией. Replace требует подтверждённого онлайн-аккаунта и заменяет его данные; не используйте его как обычный способ синхронизации. CLI legacy importer выше — отдельный административный инструмент.
